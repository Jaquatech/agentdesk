# AgentDesk: notes for coding agents

A local-only tool where a planner splits work across developer agents and a reviewer checks it. React UI, Fastify server,
`node:sqlite` database. It runs on the user's machine and listens on 127.0.0.1 only. README.md is the user manual; this file is the map and the rules.

## Commands

```bash
npm run setup        # install + build the UI
npm run dev          # server on 4317 (reload) + Vite on 5173 (/api proxied)
npm run demo         # scripted agents, no key, no cost, separate data folder (data-demo/)
npm run demo:reset   # stop a leftover demo server and clear data-demo/ (the next demo re-seeds)
npm run lint         # ESLint on server and web (CI runs lint, test, build, and `npm audit --omit=dev --audit-level=moderate`)
npm test             # server (vitest, ~52 tests) + web
npm run e2e          # browser tests (Playwright) against a fresh demo seed; needs `npx playwright install chromium` once, or E2E_BROWSER=<path to a Chrome>
npm run build        # web build + server typecheck (tsc --noEmit)
npx tsc --noEmit -p server        # quick typecheck
npx vitest run --root server test/scrum.test.ts   # one test file
```

Node >= 22.13 (uses the built-in `node:sqlite`). The UI is shadcn/ui on Tailwind (Vite, not Next.js): components in `web/src/components/ui/`, theme tokens in `web/src/styles.css` from preset `b1a09SuFE` (stone, amber, blue charts, Roboto; class `dark` on `<html>`, default dark). Icons from lucide-react. The isometric office (`web/src/office/`) is canvas drawing and is not part of that system; its chrome CSS is hardcoded at the bottom of `styles.css` so Tailwind does not restyle it.

## How the pieces fit

- **Task pipeline** (one task = one branch `task/<slug>` + one worktree under the data folder): worker builds, a commit is made only if every changed file is inside the task's allowed paths, verify commands must pass, the reviewer approves or sends fix instructions (rounds are a Setting), then push + PR (projects with a remote) and the user presses Merge. `tasks.feedback` keeps the last round's fix text so a retry continues instead of starting blind. `tasks.summary` is what the rounds that changed files did (later rounds are added as `Round N: ...`); a round that changes nothing never replaces it, since it ends up in the merge commit and the release notes.
- **Task export:** `GET /api/tasks/:id/export.md` (`taskToMarkdown` in `server/src/taskExport.ts`) renders a task and its runs' transcripts as Markdown (outputs cut, thinking left out, about 350k characters at most); the Export button in `TaskPanel.tsx` is a plain download link. Never send it anywhere: it can contain output from the user's project. A restarted round-0 task whose branch already has the work is not an error (`runTask` checks `diffAgainstBase`), and its earlier summary is kept.
- **Checks section:** `GET /api/tasks/:id` returns `checks` (`taskChecks` in `routes.ts`): the project's verify commands matched by position to the steps of the task's latest `checks` run, status `passed` / `failed` / `stopped` (the user pressed Stop while it ran; `runChecks` marks the output `exit N (stopped)`) / `not_run`, no output. The UI (`ChecksPanel` in `TaskPanel.tsx`) fetches a failed step's output from `/api/runs/:id` on click. `runChecks` stops at the first failure, so later commands are `not_run`. Failed items carry `problem` when the output shows the command itself cannot run (`commandProblem` in `verifyHelp.ts`). `verifyHelp.ts` also backs `POST /api/projects/verify-help`: suggestions by project type (`suggestVerify`), install suggestions for the setup box (`suggestSetup`), and warnings for verify lines that cannot work in the folder or have no install step (`verifyWarnings`); they are only offered in the project form, never applied.
- **Env file for checks / setup failures:** `projects.checks_env_file` names a file in the project folder (validated by `validEnvFileName`, `orchestrator/envFile.ts`). `runChecks` copies it into the worktree as `projects.checks_env_target` (default `.env`, what apps read) with `placeEnvFile` and undoes that in `finally` (removes it, or restores the bytes of a file that was already there), so it exists only while no agent runs. `runChecks` returns `setupProblem` (from `setupProblem` in `verifyHelp.ts`: command cannot run, missing env variable); the pipeline then sets `needs_attention` at once with the reason instead of starting a fix round. The worker prompt says not to run or look for env files when `checks_env_file` is set.
- **Version and release notes:** `server/src/version.ts` reads the version from the root `package.json`, the short git commit, and `CHANGELOG.md`; `GET /api/version` returns them, the sidebar footer shows `v<version> · <commit>` and the Version page (`web/src/pages/VersionPage.tsx`) renders the notes (`## version (date)`, `### group`, `- item`). Add changes to a `## Unreleased` section at the top of `CHANGELOG.md` (the Version page shows it as is) and do not bump the version until the user asks for a release. When you release: rename `Unreleased` to the version and date, bump the version in the root, `server/` and `web/` `package.json` (`npm version X --no-git-tag-version` in each) and add the matching section at the top of `CHANGELOG.md`; a test fails when they differ.
- **Third-party licences:** `server/src/licenses.ts` (pure functions: `collectPackages` from the root `package-lock.json`, `ALLOWED_LICENSES`, `licenseProblems`, `renderNotices`, `noticesCurrent`, `readThirdParty`) and `server/src/licensesCli.ts`. `npm run licenses --workspace server` writes `THIRD_PARTY_NOTICES.md` and `docs/third-party.json`; `npm run licenses:check --workspace server` (CI) fails on a licence outside the allow-list, a missing licence, or a stale notices file. `GET /api/licenses` feeds the "Packages and licences" section of the Version page. Run the generator after any dependency change and commit both files.
- **Loop guard:** `engines/loopGuard.ts` (`LoopGuard`) is fed every tool result in `apiLoop.ts`. Failed `edit_file` / `write_file` calls count per tool and are reset only by a working call of the same tool, not by reads: warn at 3, stop at 6. The same failing call (same tool and input) warns at 3 and stops at 5. Other commands that fail with different input are never stopped by it. Thresholds are constants in that file.
- **Max answer tokens:** each agent has `max_answer_tokens` (default 32 000; the migration default fills existing rows). `ApiLoopEngine` sends it as `maxTokens`. Anthropic and OpenAI-compatible providers (`providers/outputCap.ts`) retry with the cap a 400 names when the model rejects a higher one, or with 8192 when the error names none. The empty-answer note names the agent's limit. Claude CLI is unchanged: it has no output-token flag.
- **Documents:** General pages (`kind = generic`, including builtins `guidelines`, `standards`, `ui`, `models`, `cycle`; a new builtin is inserted on every open when missing, an existing one is never overwritten) have no project. A project has four slot pages (`overview`, `architecture`, `roadmap`, `setup`), an empty `decisions` section, a `releases` page per sprint (`documents.sprint_id`: `syncReleasePage` from `Scrum.writeNotes`, backfilled by `seedDocuments`; saving it copies the text back onto `sprints.release_notes` with `applyReleasePage`), and one `tasks` page per task. `seedDocuments` fills anything missing on every open. Creating a project calls `ensureProjectPages`. A task page is created from the task's title, spec, summary, and review (`syncTaskPage` from `updateTask`, including the empty update after insert, and from `PUT /api/tasks/:id`). Saving that page copies the three sections back onto the task (`applyTaskPage`) without calling `updateTask`. `#/documents/N` and `doc:N` become rows in `document_links`. `callAgent` adds `projectWikiContext` (an index: title, section, first line, length, for that project's pages and the General pages) beside the journal and passes `writeWiki`, `readWiki` and `searchWiki` whenever the call is tied to a project, in read or write mode (wiki writes do not touch the worktree; team membership is not required). `read_wiki` and `search_wiki` are offered to every agent that has `write_wiki`. General pages can be read and cannot be written. Architect and developer calls pass `wiki: "job"`, which also writes out Overview, Architecture and Setup. The planner gets the index only. Claude CLI has no custom tools: it gets the index plus the Overview page, returns `wiki` in its JSON result, and `callAgent` applies it. Every role's structured `wiki` field (planner, product manager, architect, estimate, reviewer, notes, security) and the `write_wiki` tool go through `applyWikiWrites`, which normalizes the section (`Road map`, `Overview.md`) and never updates a General page. A write that does not match is returned to the model and stored on the run. Chat calls send the last `chat_history_messages` messages (default 16, allowed 6–40, `chatHistory.ts`). `prepareHistory` asks once per window slide, not per message, for a three-line summary of what fell out. The agent is settings `rollup_agent_id` when that names an agent, otherwise the planner. A call that is not ok, or that returns no summary lines, is stored on `chats.history_rollup_failures` with `history_rollup_anchor` (the first message id still inside the window) and is not tried again until the window has slid by half a window; after three failures that chat stops trying. The chat still answers. A success writes one `project_journal` row with `kind = 'rollup'` and sets `chats.history_rolled_to` to the last message id folded in. The prompt keeps the newest 40 other journal rows and at most the 10 newest roll-up rows. `runs.prompt_chars` is the size of the system text plus the first prompt of the call. `projects.project_wiki` (default 1, read on every call) turns the project wiki off for agents: `callAgent` then lists General pages only (after one sentence saying so), passes `readWiki`/`searchWiki` with a General-only flag and no `writeWiki`, strips the update sentences from the prompt and the `wiki` property from the output tool (`withoutWikiWrites`, `withoutWikiField` in `prompts.ts`), and ignores a returned `wiki`. When you add a prompt sentence that asks for page updates, define it as a constant in `prompts.ts` and add it to `withoutWikiWrites`. Pages are never deleted and task and release pages still sync.
- **Attachments:** an upload is copied to `data/attachments/<chat id>/<id>.md` by `convertUpload` in `attachmentMarkdown.ts`. The original path is not rewritten. `attachments.status` is `converted`, `truncated`, `failed: reason`, `needs_ocr`, or empty. Text (CSV, TSV, TXT, MD, JSON, XML, logs, and the source extensions already treated as text) is copied; CSV and TSV get a column and row header. `.xlsx` is one Markdown table per sheet (`read-excel-file`, caps `SHEET_ROW_CAP` 200 and `SHEET_COL_CAP` 20; a cut sheet sets `truncated` and says how many rows and columns were left out). `.docx` is mammoth HTML then `node-html-markdown` (headings, paragraphs, lists, tables). A PDF text layer is `unpdf` `extractText` per page with `## Page N` markers. A PDF whose pages have no text is `needs_ocr` and no copy is written. `.xls` and `.doc` stay named only. `loadForPrompt` inlines the first part (about 20 000 characters, `PART_CHARS`) and says how many parts remain. `read_attachment(name, part)` is read-only and is passed from `callAgent` for every role when the call has a chat. It takes a name from that chat, never a path, and refuses any other chat. Older messages in the window stay names, plus size and part count (`earlierFileSummary`), or the stored image note when an image has one. Images are sent only with their own message: the planner and product-manager output carry `image_notes`, which `storeImageNotes` writes to `attachments.image_note` (via `Orchestrator.recordImageNotes`). The Claude CLI engine asks for them in its attachment prompt too. Settings Clear and chat deletion remove the copies with the originals (`deleteChatFiles` removes the chat folder). Pinned in `server/package.json`: `read-excel-file` 9.3.20, `mammoth` 1.13.0, `node-html-markdown` 2.0.0, `unpdf` 1.9.1 (`unpdf` 2.x needs Node 24), `@hyzyla/pdfium` 3.0.0 (renders PDF pages to PNG in `pdfPages.ts`, called by `Orchestrator.readScan`).
- **Attachment rules:** `server/src/attachmentRules.ts` (`parseRules`; defaults equal the old constants) stores the rules as JSON in the setting `attachment_rules`; `GET`/`PUT /api/attachment-rules`. Page `web/src/pages/AttachmentsPage.tsx` (sidebar group Platform settings), helpers in `web/src/lib/attachmentRules.ts`. Rules are read when a file is uploaded (conversion) and when a prompt is built (part size, images). Existing copies are not redone. The same page's "Reading scans" card stores two settings, `scan_reader_agent_id` (empty = none) and `scan_reader_max_pages` (1–50, default 10). A scanned PDF (status `needs_ocr`) is read once at upload by `Orchestrator.readScan` (`scanReader.ts` builds the prompt and the copy, `pdfPages.ts` renders the pages; called from the upload route in `attachments.ts`). With no agent chosen the status stays `needs_ocr`; a Claude CLI agent is refused.
- **Every agent call goes through `Orchestrator.callAgent`** (the Data factory's model calls are the one exception, see above): it records a `runs` row (model, tokens, cost, transcript), enforces the spending limits, and publishes activity. New kinds of agent work should use it, not call an engine directly.
- **Teams:** a project has a team, a chat can use another. No team = every enabled agent. Planner only assigns to its team's developers. Who plans: `pickPlanner` (`teams.ts`) takes `chats.planner_id`, then `projects.planner_id`, then the team's planner; it is read on every message, so a change applies at once. The chat header has the picker.
- **Scrum:** a project with `process = 'scrum'` hands chat messages to `Scrum.chat` (the planner acts as product manager). The latest message's attachments go through `Orchestrator.promptAttachments`, the same loader a plain chat uses. Items refine by themselves (product manager, architect, developer estimate) until Ready. `Scrum.start` creates the sprint branch and one queued task per item; sprint tasks start from the sprint branch, are reviewed against it, and squash-merge into it (`mergeIntoSprint`, serialized per sprint). sprint tasks whose `paths` overlap run in order: `tick` skips a queued task while a task of the sprint with overlapping paths is working (any id), or an earlier one (lower id = backlog priority) is not merged or cancelled (`blockingTask` in `orchestrator/overlap.ts`, one chat message per wait), and `cancel` ticks so a waiting task can start; `settle` completes the sprint when every task has merged; a task retried after the sprint closed (not yet released) still merges into the sprint branch: `Orchestrator.retry` puts its item back to `in_sprint`, and `Scrum.mergedLate` rewrites the notes; a retry after the release is refused; `release` merges the sprint branch into the base branch and pushes. Running-tasks tabs come from `TASK_GROUPS` in `routes.ts`: a merged sprint task is *done* until its sprint is released, then *released*. Usage per sprint attributes a run to `COALESCE(runs.sprint_id, item's sprint)`. The Scrum page is list + detail with four tabs (Backlog, Coming PI, Current PI, Releases): `web/src/pages/ScrumPage.tsx` wires the tabs, `pages/scrum/` holds `model.ts` (types, labels, `groupsByTab`, tested in `model.test.ts`), `Backlog.tsx`, `Sprints.tsx` (PI, sprint, task and plan views) and `UsageLine.tsx`. Which PI is coming or current is derived in the UI from its sprints (`groupsByTab`), there is no PI status for it. The two task views link to each other by hash: `#/tasks?group=…&task=ID` opens a task in Running tasks, `#/scrum/<project>?tab=…&sprint=ID[&task=ID]` opens a sprint or task on the Scrum page (`Route` in `App.tsx`); `/api/tasks` returns `sprint_number` and `sprint_status` for the back link.
- **Office** (`web/src/office/`): isometric canvas, no assets. `layout.ts` is pure (blocks per team or one open block, desks, lounge furniture, break `spots`, walking routes through the shared corridor; tested in `scene.test.ts`, including that routes never cross furniture or glass). `scene.ts` moves sprites and depth-sorts (`sortItems`), `props.ts` draws furniture, the invaders cabinet and slot machine (pure functions of time), `people.ts` characters, `logo.ts` the emblem. Features and logo are settings keys `office_*` and `logo_*` (defaults in `db.ts`); `/api/office` also returns teams with member ids. New furniture: add a rect to `layout.ts`, draw it in `props.ts`, add it to the route test's `rects`.
- **Data factory approval:** server `server/src/dataFactory/pipeline.ts` and `pipelineRoutes.ts` (check, approve, delete a version, per-project names and terms); only approved versions can run. UI: `web/src/pages/dataFactory/SensitiveReview.tsx` opens in the Datasets pane from `DatasetsPanel.tsx`; pure helpers (first approved version, request body, term lines, changed fields) in `pipeline.ts` next to it. Each check request has a sequence number so an older answer never replaces a newer one. The demo seed's `support-tickets` is unapproved on purpose; `e2e/demo.spec.ts` approves it.
- **Data factory files** (`server/src/dataFactory/`): import in `datasetParser.ts` (pure; jsonl, json, csv) and `datasets.ts`, upload in `routes.ts` (10 MB); models and prices in `routes.ts` and `modelFamily.ts` (free = price 0/0 or Ollama without a key); run planning in `runPlans.ts` and `estimate.ts` (cap rules); runner in `runner.ts` (`startRun`, stops at the cap); judge in `judge.ts` (prompt, `DEFAULT_RUBRIC`), `judgeConfig.ts`, `judgeRunner.ts`, `judgeRoutes.ts`; blind votes in `review.ts`; report and compare in `report*.ts`, `compare*.ts` (Markdown, CSV, Excel, JSON). Tables: `eval_datasets`, `eval_dataset_versions`, `eval_cases`, `eval_models`, `eval_runs`, `eval_run_models`, `eval_results`, `eval_judge_config`, `eval_judge_runs`, `eval_judgements`, `eval_votes`.
- **Data factory calls skip `callAgent`:** `evalCall.ts` makes each model call (no agent, tools or worktree). It checks the daily limit with `overBudget(db)` (no sprint, so the sprint limit does not apply) and inserts a `runs` row with `kind` `eval` (tested model) or `judge`, which Usage shows by kind. The demo answers in `evalCall` too; tests replace the provider with `evalHooks.chat`.
- **Demo seed** (`demoSeed.ts`): on an empty demo database `index.ts` adds a demo provider, four agents, a team and a small Scrum project (git repo in the demo data folder) with three ready backlog items, a released first sprint (two merged tasks with runs, release notes, task pages) and an active second sprint (a queued task that runs live in the demo, one needing attention, one merged; Orbit does not ask before commands so it runs unattended, Comet does), so pages, tests and browser checks have rows. Provider test and capabilities answer fixed values in demo mode. Real mode is never seeded.
- **Browser tests** (`e2e/`, `playwright.config.ts`): start a fresh demo (`demo:reset` then `demo` on port 4390) and read the seed, so a seed change can break them. CI runs them as the `browser` job. `e2e/flow.spec.ts` runs the whole sprint flow (queued task merges, retry, approval, release; about a minute, it relies on the seed's live task and on Cocoa being an interrupted round-0 task). `e2e/a11y.spec.ts` scans every page with axe in dark and light; new pages go in its list, and a new violation fails the build.
- **Demo engine** (`engines/demo.ts`) answers every tool the app uses, including the Scrum ones; extend it when you add a new tool, or the demo breaks. The active sprint's live task calls `write_wiki` once, which updates that project's Overview page.
- **Model guide ratings** are expectations unless marked "seen" (observed in real runs here). Do not mark a rating "seen" without evidence.

## Standards and gates

Full text in `docs/standards.md`; decisions (Settled / Known and open) in `docs/decisions.md`; costly mistakes in `docs/pitfalls.md`. Read the pitfalls that touch your change before you start, and add one when something bites.

- **Order of priority:** get the work done; usability; security of the user's data.
- **Use what exists:** focus, keyboard, dismissal and ARIA come from `web/src/components/ui/` or the browser, never hand-rolled in a page. Open the existing file that does the same job (the twin table in `standards.md`) before writing a new one.
- **UI work:** check current web platform guidance first (`npx -y modern-web-guidance@latest search "<2-5 words>"`, then `retrieve`), then adapt the idea to React and shadcn. Not for backend, tooling or copy.
- **Untrusted input:** model, agent, repository and tool output is shown as text or sanitized Markdown, never as HTML, and never decides a path, command or URL without validation.
- **Ask first** before a new dependency, a new migration shape, or anything touching secrets, host checks, git safety or the vault.
- **Gates:** 0 start, 1 works (`npm run lint`, `npm test`, `npm run build` exit 0; UI checked in demo mode by keyboard), 2 clean (cold read of the diff, remove generated-looking code, docs and `## Unreleased` updated), 3 release ready (usability, security, platform, project rules; run when a release is asked for). A finding is fixed with a test, or recorded in `docs/decisions.md`.
- **Pass means exit code 0,** not a reading of the output.
- **Token efficiency:** lean by default. A change that adds text to a prompt states how many tokens or characters it adds and why; anything an agent can look up (wiki pages, old messages, files) is fetched with a tool, not sent in every call. The user must be able to see prompt size and cost per call, chat and sprint; a design is adopted because it was measured here (recorded in `docs/decisions.md`). Full text in `docs/standards.md`.

## Rules

- **Migrations:** never edit an applied one; append a new string to `MIGRATIONS`.
- **Secrets:** API keys are encrypted in the vault (`crypto.ts`); values never leave the server and are never printed, logged, committed or sent to the UI. Logs carry outcomes, not values.
- **Local only:** the server binds to 127.0.0.1 and refuses other hosts and cross-site writes. Keep it that way. It also sends a strict CSP (`server/src/securityHeaders.ts`): the UI must not need inline scripts or any other host, and a change that does is a security decision.
- **Git safety:** agents work in worktrees; the user's own checkout is not touched. Only branches this tool created (`task/...`) are deleted on a remote. Commands outside an agent's allow-list need the user's approval.
- **Tests that call the API** need a `host: localhost` header and a session cookie from `POST /api/auth/setup` (username of 3+ characters). Replace the engine with `engineOverride.engine`. See `test/pipeline.test.ts` and `test/scrum.test.ts`.
- **UI changes:** check with a real browser (Playwright is fine) in demo mode; type checks do not show layout problems.
- **Keep the repo generic:** no customer, employer or other-product names in code, docs, tests or commit messages.
- Update README.md (user manual, including the Design choices section) and this file in the same change when a concept moves.
- Commits: small, imperative subject, a body that says why.
